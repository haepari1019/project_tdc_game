이 작업이 무엇인가

「16개 사각 방에 장애물을 좀 넣자」가 아니다. 맵을 구조적으로 다시 짜는 작업이고, 그 결과물은 예쁜 던전이 아니라 TDC용 맵 문법의 확정이다. 다음 작업 단위는 Upper 전체가 아니라 ENTRY 포함 8~9방짜리 새 그레이박스 한 덩어리 — 데모 맵에서 실제 맵으로 뛰는 게 아니라 「두 번째 프로토타입」이다.

기획 판단의 순서(위상 → 공간 문법 → 전투·루팅 결합 → 지역 정체성 → 높낮이)는 그대로 간다. 코드·데이터 실측 결과 세 군데만 보정했다.

①
「그 전에 데이터화」는 선택이 아니라 Phase 0이다
지금은 위상 자체가 코드다 — ROOM_SPECS·CONNECTIONS·OBSTACLE_SPECS·LOOT_CHEST_ROOMS가 전부 GDScript 상수다. 사이클 하나를 추가하려 해도 코드를 고쳐야 하고, rooms.json의 connects와 어긋나도 아무도 알려주지 않는다. Phase 1을 하려면 Phase 0이 끝나 있어야 한다.
②
새 그레이박스는 MAP-DEMO-001을 뜯지 않고 병행한다
현 맵에 QA-031 플레이어블 계약 · ci_smoke 14/14 · 열쇠문 회귀 · 허브 사다리 2개(무기고 T1 = ENC-BOSS-001, 대장간 T3 = ENC-DEEP-001 + haul_forge_coal)가 물려 있다. 제자리에서 갈아엎으면 게이트가 통째로 빨개진 채 몇 주를 간다. Phase 0이 끝나면 맵 교체는 데이터 교체가 되므로 병행 비용이 거의 0이다.
③
난이도 축은 Phase 4(지역)가 아니라 Phase 1(위상)에서 확정된다
스펙 F-006 §3.10.1이 이미 탈출로 아키타입을 갖고 있다 — route_early 교전 1~2 / route_mid 3~4 / route_deep 4~5. 현재 전역 예산 RUN_ENCOUNTER 4~5는 이 축이 경로별이라는 걸 모른 채 눌러 놓은 상태다. 경로가 생기면 difficulty 키를 RunLoadout(항상 "")이 아니라 route × world_layer가 공급하게 되고, 사문화된 Hard 12종 + spawn_table 20행이 신규 콘텐츠 0개로 되살아난다.

첫 고도화 목표를 한 줄로 루프가 있는 greybox 네트워크 + 5종의 Spatial Grammar + 위험과 루팅이 연결된 Encounter Anchor — 그리고 그것이 Blender 맵으로 갈아끼워져도 그대로 작동하는 계약.

Phase 0 — 전제

맵 계약 (Blender 확장성)

목적은 툴을 만드는 게 아니라 맵을 자유롭게 뜯어고칠 수 있게 만드는 최소 투자다. 그리고 그 「자유롭게」에는 나중에 Blender/Godot에서 아트·구조를 직접 편집하는 것이 포함된다.

소유권을 파일이 아니라 종류로 가른다

기하를 rooms.json으로 내리면 authored 맵이 오는 순간 두 벌이 다시 생긴다 — 지금 고치려는 병을 그대로 재발시킨다. 그래서 이렇게 가른다.

층내용소유자맵 교체 시
의미room_ref · connects · world_layer · route_class · grammar 태그 · encounter anchor category · loot tier · phase hintrooms.json (SSOT)유지
공간기하 · 앵커 좌표 · 오클루더 · navmesh · 조명 배치MapSource (씬)교체
다리room_ref 문자열 + 노드 이름 규약—

구현은 둘, 계약은 하나다. geometry·anchors 블록은 절차 그레이박스 전용 폴백으로 명시하고 authored 맵은 생략한다.

  • ProceduralMapSource — 현 map_demo_layout.gd. JSON에서 박스 생성. 위상·문법 반복용
  • AuthoredMapSource — Blender glTF/.blend → Godot 씬 + 마커. 아트·구조 손편집용

지금 갈아끼우면 조용히 깨지는 4곳 실측

계약은 코드 주석에만 존재한다. 실제로는 아래가 에러 없이 무너진다.

소유권 규칙 — 명사 vs 좌표

「Blender 오브젝트를 30 cm 옆으로」 같은 일까지 데이터 왕복으로 하면 손해가 명백하다. 사람이 2초에 하고 즉시 눈으로 확인하는 일을, 나는 수정 → 재생성 → 스냅샷 → 판독으로 수십 초를 쓴다. 그래서 경계를 단계가 아니라 대상으로 긋는다.

규칙에이전트는 명사와 관계를 쓰고, 에디터는 좌표를 쓴다.

데이터 (에이전트)씬 · 에디터 (사람)
room_ref · connects(위상) · route_class메시 위치 · 회전 · 스케일
encounter anchor category · loot tier프롭 배치 · 데코 산포
앵커의 존재와 개수(「이 방에 loot 앵커 3」)앵커 마커의 실제 위치
ID 등록 · spawn_table 행 · phase hint머티리얼 · 라이트 미세조정
판정 기준 = 불변식이 계산된다판정 기준 = 보기에 맞다

핵심은 authored 맵의 좌표가 데이터에 없어야 한다는 것이다. 앵커는 씬의 Marker3D이고 데이터는 그걸 이름으로 참조한다. 그러면 MK_loot_1을 기둥 뒤로 끌어다 놓아도 데이터는 한 글자도 안 바뀐다 — 충돌이 성립하지 않는다. 검증은 좌표가 아니라 「마커가 3개 있고 · 방 안이고 · navmesh 위인가」를 묻는다.

「에디터 = 뷰어」는 생성된 것에만 적용된다

단계저작 표면메커니즘
그레이박스데이터 (에디터는 뷰어)@tool 빌더가 owner를 설정하지 않고 노드를 붙인다 → 3D 뷰포트엔 보이지만 .tscn에 직렬화되지 않는다. 박스 크기는 취향이 아니라 설계 수치이므로 데이터가 소유
아트 전환씬생성기가 만들지 않으니 파괴할 일도 없다. generated / authored 분리 — 재생성은 generated 서브트리만 건드린다

강제는 등호가 아니라 경로로 건다 — 에이전트 도구는 data/와 생성 서브트리에만 쓰고, authored 방 .tscn에는 쓰지 않는다. 사람이 한 시간 만진 방을 재생성이 날리는 사고는 규칙이 아니라 경로로 막는다.

그 대가로 붙는 규약 하나 — 콜리전 프록시는 반드시 메시의 자식 오클루더를 콜라이더에서 유도하므로 끌어다 놓는 순간 다음 로드에 안개가 따라온다(손 튜닝의 자유를 데이터 부채 없이 사는 방법이 그거였다). 다만 프록시를 따로 두고 메시만 옮기면 보이는 벽과 막는 벽이 어긋난다. Godot -col 임포트가 만드는 계층이 이미 그 모양이라 기본은 안전하다.

아트 단계에서 에이전트가 하는 일

「하나를 옮기기」는 사람이 빠르고 「같은 걸 예순 번 옮기기」는 에이전트가 빠르다. 경계는 반복성과 판정 기준이다.

  • 벌크 변환 — "모든 방 횃불을 벽에서 0.5 m 띄워"(손 60드래그 = 스크립트 1개)
  • 규약 검사·수정 — 이름 규약 위반 · 앵커 누락 · 프록시 없는 벽 · navmesh 밖 앵커
  • 문법 복제 — "이 방 기둥 배치를 같은 문법의 다른 3방에"
  • 비시각 배선 — room_ref 결속 · ID 등록 · spawn_table 행 · 루트 분류
  • 씬 diff 리뷰 — 커밋에서 무엇이 움직였는지 텍스트로

반대로 판정 기준이 「보기에 좋다」인 건 전부 사람이다. 스냅샷의 해상 한계가 곧 에이전트의 작업 단위이기도 하다 — 방 단위 배치·개구부·동선까지가 보이고, 기둥 30 cm는 안 보인다.

Phase 1

위상 — 루프와 복수 탈출로

가장 큰 구조적 문제다. 현재는 어느 쪽을 가든 왔던 길로 돌아와야 하고, 플레이어의 경로 선택이 사실상 「여기 갔다 올까 말까」 하나뿐이다. 중요한 건 루프 자체가 아니라 되돌아가는 방법을 선택할 수 있다는 것이다.

초안 그레이박스 — 9방 · 사이클 3

                     +--------+--------+
                     | EXT-B  |        |     EXT-B  심층 탈출 (route_deep)
                     +--------+  DEEP  |     DEEP   확정 교전 + 최고 보상
                     |  GATE  |        |     GATE   확정 정예 · 위험 관문

            +--------+--------+--------+     HALL   중앙 분기 (Open + Flank)

            +--------+                       EXT-A  조기 탈출 (route_early)

연결 11개 / 방 9개 → 사이클 = 11 − 9 + 1 = 3.

사이클경로의미
AREC → OBJ → HALL → ENTRY → REC목표 왕복 강제 제거 — 다른 길로 돌아온다
BOBJ → FOR → HALL → OBJ보상 우회로 — 위험을 사면 빨리 온다

  • OBJ가 관통방이다 — 연결 4개(GATE · REC · FOR · HALL). 현재 connects: []인 dead end 열쇠방과 정반대
  • 탈출 2점 — EXT-A는 ENTRY 옆(조기), EXT-B는 GATE 또는 DEEP을 통과해야 도달
  • 위험 경로가 지름길이다 — FOR을 지나면 HALL ↔ DEEP이 짧아진다
  • dead end는 명확한 보상이 있을 때만 — 이 초안엔 없다

백레이어를 Phase 1에 넣는다. 레이어는 「구획이 하나 더」가 아니라 위상 축이 하나 더라, 나중에 얹으면 우리가 지금 피하려는 그 실수(구조를 다 짜고 나서 축을 추가)를 반복한다.

Phase 2

Spatial Grammar 5종

방마다 독특한 기믹을 만들면 콘텐츠 제작비가 터진다. 대신 파라메트릭 장애물 템플릿 5~7개를 만들고, 방을 RM-ADV-03이 아니라 「Choke + LOS」 「Open + Flank」 「Split + Backline」으로 구별하기 시작한다.

  OPEN                 CHOKE                LOS-BROKEN
  +------------+       +----+  +----+       +------------+
  |            |       |    |  |    |       |    ##      |
  |      E     |       |    E  E    |       |  P      E  |
  |            |       |    |  |    |       |        ##  |
  |  P         |       +----+  +----+       |  ##        |
  +------------+                            +------------+
   광역전 유리          전열(탱커) 가치↑      캐스터·저격 대응

  SPLIT                FLANK                BACKLINE POCKET
  +-----+ +-----+      +------------+       +------------+
  |     | |     |      |      E     |       |   E    E   |
  |  P  +-+  E  |      +---+    +---+       +------+-----+
  |     | |     |      |   P    P   |       |  P      p  |
  +-----+ +-----+      +------------+       +------------+
   개별 이동 오더        주경로 + 측면        후열 안전지대
E 적 · P 전열 · p 후열 — 방 하나에 문법 1~2개만 쓴다(겹칠수록 읽기가 어려워진다)

하나의 grammar가 LOS 차단 · navmesh 구멍 · 안개 오클루더 · 상자 앵커를 동시에 공급한다 (현행 get_occluder_footprints가 이미 그 구조다). 한 번 만들면 네 곳이 값을 받는다.

여기서 AI 한 가지를 같이 넣지 않으면 문법이 반쪽이 된다 현재 원거리 적(standoff)은 사거리까지만 좁히고 LOS를 되찾으려는 행동이 없다. LOS가 끊기면 investigate로 눈먼 추격을 한다. 기둥·초크를 넣으면 플레이어만 이득을 보고 적은 벽 뒤에서 멍청해 보인다. 「원거리 적이 LOS 회복 위치로 재배치」 한 가지는 grammar와 같은 패스에 넣는다.

같이: aggro_wake_buffer_m(4.0 m, F-006 §3.2.3, 현재 미구현). 초크 뒤 즉시 어그로는 스펙이 금지한 배치인데, 문법을 넣는 순간 그 배치가 쉬워진다.

진행 게이트를 확률에서 뺀다 무기고 T1(ENC-BOSS-001)과 대장간 T3(ENC-DEEP-001)가 각각 32 % · 40 %로만 생성된다. 「어려운 관문은 맵의 방이 소유한다」는 M6 판정과 확률 추첨이 서로를 갉아먹고 있다. 「반드시 존재」이지 「반드시 싸움」이 아니다 — 관문은 경로 선택으로 남고, 랜덤성은 그 전투의 구체적 형태에 둔다.

루팅 — EV를 보존한 채 재분배

상자 18 → 10은 재화 −45 %다. SQUAD_HAUL_MULT = 0.2 때문에 상자가 주 공급원이고, 재료 11종이 시설 9 + 스킬트리 2를 먹인다. 총 기대치는 16~20 밴드로 유지하고 티어로 옮긴다.

순서가 중요하다. Spatial Grammar가 게임플레이 문법이고, 지역 테마는 그 문법을 표현하는 방식이다. 뒤집으면 「병영이니까 침대 놓고 무기 rack 놓고…」가 되기 쉽다.

Phase 5

수직·다층 구조 + 환경 반응

방향 전환 (2026-08-24) 원안은 「1.5 m 전술 단차 실험」이었고 「2층은 불가능」이라고 적었다. 그 판정은 과했다 — 막혀 있던 건 높이가 아니라 XZ 중첩이었고, 한 번에 한 레이어만 활성이면 중첩이 문제되지 않는다. 스펠렁키식 백레이어를 채택하고, 위상 축이므로 Phase 1에 편입했다. 여기 남는 것은 시스템 구축이다.

선행 완료 — 절대 Y 걷어내기 DRIFT-167

LOS_EYE_Y = 1.0이 월드 절대 좌표였다. 바닥이 −6 m인 방의 벽은 y ∈ [−6, −2.5]라 그 높이를 안 가려 오클루더에서 통째로 빠진다 — 안개 없는 방이 조용히 생긴다. 그리고 게이트가 못 잡았다: 맵과 스모크가 같은 절대 규칙을 써서 양쪽이 사이좋게 0을 반환해 「미일치 0」으로 통과했다.

반증 확인 — eye를 절대값으로 되돌리면:
  FAIL  바닥 y=-6 방의 벽이 오클루더로 잡힌다 (절대 Y였으면 0개)
  FAIL  지상 1 + 지하 1 = 오클루더 2개 (1)
합성 authored 씬에 바닥 y=−6 방을 세워 건 회귀 테스트

같이 들어간 불변식 2종: 같은 레이어 방 XZ 중첩 없음(레이어 축이 들어오면 레이어별로 갈린다 — 다른 레이어끼리는 겹쳐도 되고 그게 요점이다) · 방마다 오클루더 ≥ 1(총량 대조가 0 = 0으로 통과하던 구멍).

반대 의견 · 걸리는 것

① 루프는 공짜가 아니다 적이 런 시작 시 전부 배치되어 방 안에서 잠들어 있는 현 모델에서는, 루프를 뚫어도 「뒤에서 나타나는 압력」이 생기지 않는다. Patrol이 방을 넘지 않으면 새 길은 그냥 빈 지름길이다. Phase 1에 patrol graph가 동반되어야 하는 이유다.

② 상자를 줄이면 재화가 줄어든다 상자는 장식이 아니라 시설 9종 + 트리 2종의 유일한 주 공급원이다(분대 드롭 ×0.2). 구조를 바꾸되 EV는 16~20 밴드로 보존하고, 경제 재조정은 별도 판단으로 분리한다.

③ 문법은 플레이어에게 유리하게 비대칭이다 LOS 차단은 적 AI가 쓸 줄 모른다. 원거리 재배치 없이 기둥만 늘리면 난이도가 조용히 내려간다.

④ 계약을 약속으로 두면 나중에 8배로 갚는다 Phase 0을 건너뛰고 8방을 더 지으면, Blender 전환 시점에 고칠 대상이 8배가 된다. 지금 치는 값(오클루더 유도 + 임포트 대응 + 계약 강제)이 그때보다 싸다.

⑤ 부수 발견 — 스폰 좌표가 navmesh 동기화 전에 질의된다 계측기를 붙이자마자 나온 것: NavigationServer navigation map query failed because it was made before first map synchronization (combat_controller.gd:1139 map_get_closest_point, prespawn 경로). 첫 프레임 스폰 스냅이 무효화된다. ci_smoke의 ERRPAT에 이 부류가 없어 15/15는 초록인 채로 계속 난다. 헤드리스 루프가 있다고 다 잡히는 게 아니라는 실례 — map_smoke가 흡수할 대상.

⑥ 이 문서는 초안이다 9방 그레이박스 배치 · 문법 5종의 선택 · anchor 카테고리 목록은 전부 초안이며, 스킬 단위 감독과 마찬가지로 채택·변경 판단은 기획이 소유한다. 여기 있는 것은 실측과 그 위에서 성립하는 선택지다.
