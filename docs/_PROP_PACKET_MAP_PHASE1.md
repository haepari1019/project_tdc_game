### A. `routeClass` — 방이 어느 탈출로에 속하는가 (schema)

**스펙에 이미 있는 것:** `F-006` §3.10.1이 탈출로 아키타입 3종(`route_early` / `route_mid` / `route_deep`)과 **경로별 교전 수**(1~2 / 3~4 / 4~5)를 정의한다. `DBP-DEFAULT-001`은 `extractionRouteRef`를 갖는다.

**없는 것:** **방이 어느 경로에 속하는지 표기하는 필드.** 그래서 「이 런의 경로가 무엇인가」를 런타임이 알 수 없고, 게임은 전투 예산을 **전역 4~5**로 눌러 놓았다(경로 개념 없음).

**제안:** Room 레벨 `routeClass[]`(복수 — 한 방이 여러 경로에 속할 수 있다). `DBP` 인스턴스는 `extractionRoutes[]`와 방 태그가 정합해야 한다.

**실측:** 현 맵은 탈출 지점 1개·경로 1개. 임계 경로 기대 전투 **1.02회**(런 4.5 중), 남쪽 사슬이 전투 가중치의 **35 %**를 갖는데 임계 경로가 지나지도 않는다.

---

### B. **난이도 축을 방·경로가 소유한다** — 옵션 2 채택 ⚠ `rule`

**결정(2026-08-24):** 옵션 2 + **2단 구조**. 기획 의도가 「맵 난이도 분기」가 아니라
**「메트로배니아식 진입 조건으로 잠긴 방 → 열면 그 안이 더 어렵다」**임이 확인됐다.

```
① 진입 조건(entryRequirement)  ── 잠금 ──▶  ② difficultyProfile 오버라이드
   무엇으로 여는가                            열린 뒤 그 안이 얼마나 어려운가
```

**둘은 짝이다.** ①만 있으면 그냥 잠긴 빈 방이고, ②만 있으면 **모르고 걸어 들어가는 난장판**이 된다.
초안 판단은 옵션 1(티어 축)이었으나 기획 판정으로 옵션 2 — 티어라는 중간 어휘를 만들지 않고
M6 판정(「어려운 관문은 맵의 방이 소유한다」)을 직접 표현한다.

#### ① 진입 조건 — **새 개념이 아니라 적용 범위 확대**

스펙은 이미 진입 조건 어휘를 갖고 있다. 다만 **탈출 지점**과 **보스 레이드 입장**에만 붙어 있다:

| 기존 조문 | 내용 | 지속성 |
|---|---|---|
| `F-006` §3.10 | Point별 `extractionActivationRule` — `always`·`onEntry`·`onObjectiveComplete`·**`requiresItem`**·**`onBossKey`** | 런 내 |
| `GIMMICK-DEMO-01` | 열쇠 상자 → 문 (게임에 **이미 구현**) | 런 내 |
| §3.1.8 | `mainBossAccessGrant: onExtractionSuccess` · `bossRaidEntryRequiresAccess` | **프로필 지속** |
| §3.11.1 | `locksPreviousRooms` | 방 잠금 어휘 |

→ **같은 어휘를 일반 `Room`으로 넓힌다.** 「없던 걸 만든다」가 아니라 「이미 있는 걸 제자리에 놓는다」다.
탈출 지점 활성 조건과 방 진입 조건이 **같은 문법**을 쓰게 되는 것도 이득이다.

**스키마 초안 — `entryRequirement` (RM 레벨, 선택 필드)**

```yaml
entryRequirement:
  rule: requiresItem | onBossKey | onObjectiveComplete | onFacilityTier | onAccess
  ref: <스펙 ID>              # KEY-DEMO-01 · facility_id · quest_id …  (새 ID 발명 금지)
  scope: run | profile        # ▼ 아래 두 종류
  consumeOnUse: true|false    # scope=run 에서 주로 true (열면 소모)
  grantOn: onExtractionSuccess | onOpen   # scope=profile 확정 시점
```

**기획 결정: 두 종류를 다 쓴다.**

| | `scope: run` — 소모성 | `scope: profile` — 영구 해금 |
|---|---|---|
| 여는 것 | 이 런에서 얻은 열쇠·해체 도구 | 시설 티어 · 의뢰 완료 · Access |
| 다음 런 | **다시 잠긴다** | 계속 열려 있다 |
| 만드는 압력 | *「이번 런엔 어느 문을 열까」* — 소모성이라 하나만 | *「저기를 뚫으려면 무엇을 갖춰야 하나」* — 메타 목표 |
| 선례 | `GIMMICK-DEMO-01` (구현됨) | `mainBossAccessGrant` |

**✅ `grantOn: onExtractionSuccess` 확정(2026-08-24).** 문을 **연 순간** 영구 해금이면 「열고 죽어도 이득」이
되어 익스트랙션 긴장이 빠진다. 스펙의 기존 영구 해금 사례(`mainBossAccessGrant`)와 같은 원칙 —
**들고 나가야 내 것**. 게임 배선은 **탈출 성공 정산 시점**에 프로필 플래그를 남기는 것이 실체다.

**🔴 재방문 가치 완화(제안):** 영구 해금이 되면 그 방은 이후 그냥 「어려운 방」이 된다.
둘을 **겹쳐 쓰면** 해소된다 — **접근은 `profile`로 영구히 열고, 그 안의 보상은 `run` 소모성으로 한 번 더 잠근다.**
「둘 다 쓴다」는 판정이 이 조합을 자연스럽게 만든다.

**문제(실측):** 도달 가능 ENC **12/24**. 난이도 선택 UI가 M6에서 폐기돼 `RunLoadout.difficulty`가 항상 빈 문자열
→ manifest 기본값 `Normal` 고정 → spawn_table의 **Hard 20행 + `ENC-HARD-*` 12파일이 영영 안 나온다.**

**충돌하는 조문 — `F-006` §3.1.2:**

> `Normal`, `Hard`, `Extreme` 등은 **던전 시작 전** 플레이어가 고르는 **난이도 프로필**이다.
> - **한 런 안에서** `Normal` 구역을 지나 `Hard` 구역으로 "진행"하지 **않는다**.

이 조문의 전제(**런 전 플레이어 선택**)가 M6에서 사라졌다. 선택 UI가 없는데 「선택한 프로필은 런 내내 불변」만
남아 있어, **존재하지 않는 메커니즘을 지키느라 콘텐츠 절반이 잠긴** 상태다.

#### ⚠ 영향 범위 실측 — `difficultyProfile` 참조 **41개 파일**

무제한으로 손대면 패킷이 터진다. **가장 좁은 형태**로 집행할 것을 제안한다.

| 대상 | 처리 | 사유 |

| `F-006` §3.10.1 | 한 줄 추가 — 경로 아키타입이 프로필을 공급 | §A와 짝 |
| `LDG-001` §8 | `difficultyProfile` 행 추가(RM/Pool 오버라이드) | 필드 등록 |
| `DBP-DEFAULT-001` §3 | 템플릿 주석 — 런 기본값 + 방/경로 override | 양식 |

| `F-010` 배치 단계 | **문구 갱신**(삭제 아님) — 「난이도 선택 UI」 → 「난이도 축은 지역·진입 조건이 소유(`F-006` §3.1.2)」 | 판정 2026-08-24. 삭제하면 M6에 무슨 일이 있었는지가 사라진다 |

**① `D-015`가 이유 있는 부작용이다.** 런 상태가 `difficultyProfile`을 **하나** 들고 있는데, 방마다 다를 수 있게
되면 그 값이 무엇을 뜻하는지 모호해진다. → 필드를 **「런 기본값(방/경로 override의 폴백)」**으로 재정의만 하고
스키마는 그대로 둔다. 삭제하면 조기 탈출·정산·QA 계약이 같이 흔들린다.

**② ENC 21개 파일은 손대지 않는다.** 헤더의 `difficultyProfile: Hard`는 **「이 ENC는 Hard 규모다」**로 이미
기능하고 있다 — 누가 그 값을 정하느냐만 바뀌지, ENC 자신의 의미는 그대로다. 21파일을 여는 순간 패킷이
검수 불가능해지고, 얻는 것이 없다.

#### 제안 본문 — `F-006` §3.1.2 교체안 (초안)

> #### 3.1.2 Difficulty profile (공간이 소유 — NOT run phases)
> `Normal`, `Hard`, `Extreme` 등은 **공간이 소유하는 난이도 프로필**이다.
> - **런 기본값**은 `Run Contract`가 정한다(`D-015` `difficultyProfile` = 폴백).
> - **`Room`/`extractionRoute`가 이를 오버라이드한다.** 한 런 안에서 `Normal` 구역을 지나 `Hard` 구역으로
>   **진행할 수 있다** — 어려운 관문은 **토글이 아니라 맵의 방**이 소유한다.
> - 오버라이드는 **경로 선택으로 노출**되어야 한다(`F-006` §3.10 — 보스 격파는 탈출 전제가 아니다).
>   플레이어가 모르고 밟는 난이도 상승은 금지한다: 진입 전 **전조**(조명·`zoneAmbientTier`·문/관문 연출)를 둔다.
> - 인지 부하 상한(`F-024`)은 **오버라이드 후 값**으로 검증한다.
>
> **폐기:** 「한 런 안에서 Normal 구역 → Hard 구역으로 진행하지 않는다」(M6에서 난이도 선택 UI가 사라져
> 전제가 소멸). 이력은 §3.1.6 Legacy note에 남긴다.
>
> **resolve 순서(개정)**
> 1) `Run Contract`의 런 기본 `difficultyProfile` 확정
> 2) 인스턴스 생성 시 **방·경로 오버라이드** 적용 → 그 방의 유효 프로필 확정
> 3) Pool의 규모/티어 참조 + 유효 프로필로 `docs/combat/` 테이블에서 `ENC-###` resolve
> 4) `F-024` 인지 부하·Hazard 밀도 가이드 만족 검증

**가드레일 — 잠금이 곧 예고다(단, 강제하지 않는다).** 초안에는 「진입 전 전조 필수」를 넣었는데
**잠긴 문 자체가 전조**이므로 조항을 바꾼다: **「`difficultyProfile` 오버라이드는 `entryRequirement` 동반을 기본으로 한다」.**

**판정(2026-08-24): 잠금 없는 난이도 방도 허용한다** — 명시적으로 막지 않고 조절로 다룬다.
그러면 그 방들에 한해 **원래의 전조 요구가 살아 있어야 한다**(잠금이 없으니 예고할 게 없어진다):

> `entryRequirement` **없이** `difficultyProfile`을 올린 Room은 진입 전 **전조**(조명·`zoneAmbientTier` 하강 ·
> 문/관문 연출)를 둔다. 플레이어가 모르고 밟는 난이도 상승은 `F-006` §3.2.3(의도치 않은 전투 개시 완화)과
> 같은 성격의 문제다. — **강제(MUST)가 아니라 권장(SHOULD)**, LD 체크리스트 항목.

**🔴 새 게이트 불변식 — 데드락 방지.** 메트로배니아에서 제일 흔한 사고가 **「열쇠가 잠긴 방 안에」**다.
`map_smoke`가 그래프로 기계 검증할 수 있다: 잠금을 **간선 조건**으로 두고
*「ENTRY에서 시작해 그때까지 획득 가능한 것만으로 모든 필수 목표·탈출에 도달 가능한가」*.
`scope: profile` 잠금은 **처음 방문 시점 기준**으로 풀 수 있어야 한다(안 그러면 신규 플레이어가 막힌다).

### D. `encounterAnchor.category` — 공간 역할이 **스폰 여부**를 정한다 (rule/schema)

**스펙 현황:** `F-006` §3.2.4가 `placementBehavior` 3종(`Fixed`/`Patrol`/`AmbushHold`)을 정의한다. 그런데 이건 **배치 거동**이고, **「이 방에 전투가 존재하는가」를 정하는 축은 없다.**

**실측(충돌):** 허브 진행 게이트 2개가 확률에 걸려 있다 — 무기고 T1(`ENC-BOSS-001` 처치)은 **32 %**, 대장간 T3(`ENC-DEEP-001` 처치)는 **40 %**로만 생성된다. 게다가 그 방에 도달하려면 임계 경로를 벗어나 왕복해야 한다. 「어려운 관문은 맵의 방이 소유한다」는 설계 의도와 가중 추첨이 서로를 갉아먹는다.

**제안:** Room/Pool `encounterAnchor.category` 7종. **카테고리가 스폰 여부를**, 그 안에서 **spawn table이 구체 편성을** 정한다.

| category | 스폰 | 의미 |
|---|---|---|
| `mandatory_threat` | 100 % | 임계 경로의 필수 교전 |
| `gated_elite` | 100 % | **잠긴 방의 확정 정예** — 추첨에서 제외 + `entryRequirement` 동반(§B) |
| `optional_threat` | 가중 | 보상 루트 |
| `patrol_route` | 경로 | `patrolGraphRef` 순회 |
| `ambush_candidate` | 가중 | `AmbushHold` 후보 |
| `third_faction_candidate` | 확률 | `F-028` exit 수렴 |
| `safe` | 0 % | 진입·조기 탈출 |

**§B와의 관계:** `gated_elite`는 원래 「확률 추첨에서 제외 = 항상 존재」만 뜻했다. §B의 `entryRequirement`가 생기면서 **접근 제어까지** 갖는 카테고리로 정확해진다 — 잠긴 방이므로 「모르고 밟는」 경로가 아니고, 그래서 확정 정예가 정당하다.

**핵심 구분(문서에 명시 제안):** **「반드시 존재」이지 「반드시 싸움」이 아니다.** 관문은 경로 선택으로 남고, 랜덤성은 그 전투의 **구체적 형태**에 둔다. `F-006` §3.10(보스 격파는 탈출 전제가 아니다)과 정합.

**연동:** `F-028` `thirdFaction.exitConvergenceRouteRef → route_deep`이 이미 스펙에 있는데 게임은 **랜덤 전투방에 코드 상수로 주입**하고 `P-3RD-01`은 고아다. `routeClass`(§A)가 생기면 이 스펙 조항이 그대로 실구현된다.

### G. **레이어(백레이어) 축 + 계단 전이** (rule/schema)

**결정(2026-08-24):** 스펠렁키식 **백레이어** 채택 — 하위 구획을 옆으로 치우지 않고 **같은 XZ 발자국에 겹쳐** 두고
레이어를 전환한다. 한 번에 **한 레이어만 활성**이다.

```
포털  = 런 경계 (진입 / 탈출)          ← 기존 Extraction Point
계단  = 같은 런 · 같은 맵 안의 워프     ← 신규
```

#### 왜 겹치는가 — 예산이 뒤집힌다

옆으로 치우면(displacement) 안개 바운딩 박스가 커진다. 현재 맵은 이미 **바운딩 32,909 m² 중 바닥 10,116 m²
= 69 %가 빈 공간**이다. **겹치면 구획을 몇 개 쌓아도 XZ 발자국이 그대로**라 텍스처가 안 커진다.
Phase 1의 「사이클 ≥ 2」도 **XZ를 안 늘리고** 달성된다(지상 A→B의 평행 간선을 아래층이 만든다).

#### 스펙 어휘와의 관계

| 개념 | 스펙 | 판정 |
|---|---|---|
| 로드 단위(지역) | `mapId` | ✅ 그대로 — 레이어는 **맵 안**이다 |
| 테마 구획 | `conceptZone` | ✅ 그대로 — **`layer`와 직교**한다(한 레이어에 여러 zone 가능) |
| 포털 | `Extraction Point` + `extractionActivationRule` | ✅ 역할 확장뿐 |
| **레이어** | 없음 | 🔴 **신설** — Room `layer` |
| **계단(레이어 전이)** | 없음 | 🔴 **신설** — `F-006`에 한 줄 |

`conceptZone`을 레이어로 쓰지 않는다는 점을 명시해야 한다. 이름이 비슷해 섞이기 쉬운 자리다.

#### 전이 규칙 — **파티는 찢지 않는다**

> 레이어 전이는 **행동 가능한 멤버 전원의 결집**을 조건으로 한다.
> **down / MIA 멤버는 따라오지 않는다** — MIA는 `down`으로 전환되고 **쓰러진(이탈한) 그 자리에 남는다.**
> `F-007` §3.6.2 `extractionCohesionRule` · `F-003` `unbound_anchor_max_m`과 **같은 모양**을 재사용한다.

- **다운/MIA가 있어도 전이는 막히지 않는다**(판정 2026-08-24) — 대신 **두고 간다.**
- 다른 레이어로 간 파티는 그를 **부활시킬 수 없다. 돌아와야 한다.**

**전이 시 남겨진 멤버는 기존 상태를 그대로 유지한다**(판정 2026-08-24). 강제 전환은 없다.

| 두고 갈 때 상태 | 그동안 | 돌아왔을 때 |
|---|---|---|
| `MIA` — **살아서 이탈** | ✅ **적에게 노출된다** | 무사할 수도, **`down`이 되어 있을 수도** 있다 |
| `down` — **이미 쓰러짐** | 더 나빠지지 않는다 | 그대로. **회수·부활 대상** |

`down`은 **선택지가 아니라 결과**다 — `MIA`가 죽으면 `down`이 된다. 그래서 「안전하게 `down`으로 두고 간다」 같은
선택은 성립하지 않는다.

**❌ 폐기된 초안:** 「비용이 크면 `MIA`를 `down`으로 즉시 전환」. 그건 폴백이 아니라 **성능을 위해 캐릭터를 죽이는
것**이다. 비용이 문제라면 시뮬레이션을 단순화하는 쪽으로 풀지, 상태를 떨어뜨려 풀지 않는다.

⚠ **실제 비용 동인은 CPU가 아니다.** 그 레이어는 이미 적이 돌고 있으므로(「전 레이어 실시간」 결정) 유닛 하나가 더
도는 건 미미하다. 비싼 쪽은 **파티 멤버 상태 기계** — 「존재하지만 조작 불가, 다른 레이어에 있음」 상태가 포메이션·
추종 AI·스왑·HUD 가정을 건드린다.

**필요한 가드는 이미 스펙에 있다.** `F-001` §3.6이 **MIA를 스왑 차단 사유**로 두고 있는데 게임은 미구현이다
(`run_controller.can_swap()`이 무조건 `true`). 레이어가 그 미구현을 **필수**로 만든다 —
다른 레이어의 MIA 멤버로 스왑되면 그 순간 「조작 가능한 파티가 두 레이어에 나뉜」 상태가 되어 전제가 깨진다.
- **「파티를 찢지 않는다」와 충돌하지 않는다** — 찢김은 *조작 가능한* 멤버가 두 공간에 나뉘는 것이고,
  쓰러진 몸은 조작 대상이 아니다. 그건 찢김이 아니라 **회수 부채**이고 정확히 `F-007`(Recovery / Loss Bundle)의 축이다.
- 아키텍처도 그대로 지켜진다: **행동 가능한 파티는 언제나 한 레이어**에 있으므로 **활성 레이어가 하나**다.

**이 규칙이 만드는 압력**

| | |
|---|---|
| 내려가기 전 | **부활시키고 갈 것인가, 두고 갈 것인가** — 결집 조건이 실질을 갖는다 |
| 두고 가면 | 회수 부채가 남는다. **잠긴 관문 뒤에서 쓰러졌다면** 무거운 결정이 된다 |
| 탈출 시 | `F-007` `extractionSurvivorGate: atLeastOne` — 두고 나갈 수 있고, 대가를 치른다 |
| ✅ 치즈 차단 | 계단이 **MIA 회수 수단이 되지 않는다**(초안에서 감시 대상으로 적었던 것이 원천 소멸) |
| 상태 선택 | **합류·부활시켜 데려갈까, 그대로 두고 갈까.** `MIA`를 두고 가는 건 **도박**(죽어 있을 수 있다), `down`을 두고 가는 건 **부채**(회수해야 한다) |

**해소:** ~~비활성 레이어의 `down` 멤버를 적이 건드릴 수 있는가~~ → **`down`은 시체라 건드릴 수 없다.
위험에 노출되는 것은 `MIA`(생존) 쪽이다.**

#### 층을 넘는 것은 **3세력뿐**

> 일반 던전 몬스터(`faction: Dungeon`)는 **레이어에 고정**된다 — `patrolGraphRef`는 자기 레이어 안에서만 돈다.
> **`F-028` 제3세력만 계단을 사용**해 레이어를 넘는다.

`F-006` §3.2.4가 이미 *「본 절은 표준 몬스터 전용이며 `F-028` Third Faction과 규칙·템플릿을 공유하지 않는다」*고
분리해 놨으므로 **명분이 이미 서 있다.** 얻는 것:

- 파티는 결집해야 층을 넘는데 3세력은 자유롭다 → **비대칭 압력**
- 파티가 볼 수 없는 아래층에서 벌어진 일이 **위층으로 올라온다** → `F-028` 창발이 **깊이 축**을 얻는다
- 비용은 작다 — 런당 **1분대**(`maxConcurrent: 1`)만 층간 이동을 할 줄 알면 된다

#### 시뮬레이션 예산

「전 레이어가 동시에 실시간 진행」이 결정이므로 **분대 수와 AI 틱이 레이어 수만큼 늘어난다.**
`F-028` `offscreen.roomEventBudgetPerTick`(현 DBP 값 6)이 그 자리다 — 실측 후 튜닝 대상으로 명시.

#### 게임 소유(전파 아님)

레이어별 안개 탐색 누적 · world 콜리전 비트 분리 · 레이어별 `NavigationRegion3D` · 유닛 `layer` 속성 ·
미니맵 층 표시 · 계단 앵커(`transitions` `role: stairs`, `to: {layer, room}`) · 페이드 워프.
선행 작업(절대 Y 상대화 + 불변식 2종)은 **DRIFT-167로 완료**.

## 2. 신규 ID 발급 (§F)

**결정(2026-08-24):** `PROTO` 같은 임시 접두사를 쓰지 않는다 · 지역 컨셉은 아직 미확정이라 **임시로 두고 나중에 스위칭**한다.
→ 두 판정을 동시에 만족시키는 형태를 아래에서 정리한다.

### ⚠ 먼저 — 지역명이 스펙에 아예 없다

병영·수문·기록원·제련소는 **기획 코멘트에만 있고 스펙에 없다**(`docs` 전수 grep **0건**).
`LAY-UPPER`는 톤·비주얼·전조만 정의하고 **구체 장소를 하나도 명명하지 않는다**.
→ 지역 어휘를 **새로 만들어야** 한다는 뜻이다. 다만 컨셉이 미확정이므로 **이 패킷에서는 만들지 않는다** — 아래 「해법」대로 ID를 지역명과 분리하고, 어휘 신설(`LAY-UPPER` §7 또는 신규 Zone 문서)은 컨셉 확정 시로 이연한다.

### ⚠ 그리고 — ID 충돌이 이미 강제 조건이다

`MAP-DEMO-001`은 **유지**한다(회귀 게이트·허브 사다리 T1/T3). 두 맵이 공존하는데
`id_registry.room_refs`는 **평면 전역 목록**이라, 새 맵은 `RM-ENTRY-01`·`RM-OBJ-01`·`RM-EXT-01`·
`RM-ADV-01..09`·`RM-MID-01`·`RM-BOSS-01`·`RM-DEEP-01`·`RM-ROUTE-01`을 **재사용할 수 없다**.

역할 기반 이름(`RM-ENTRY-##`)을 이어 쓰면 번호만 늘려 가며 충돌을 피해야 하는데, 그러면
「01은 데모, 02는 신맵」이라는 **문서 어디에도 안 적힌 규칙**이 생긴다. **지역명 채택이 이 문제를 자연히 없앤다.**

### ⚠ 그런데 — **임시 이름을 ID에 넣으면 나중에 못 바꾼다**

판정: *「지역 컨셉이 덜 잡혔으니 임시로 잡고 임시 표기 후 나중에 스위칭」*.
의도는 맞지만 **ID에 임시 이름을 넣으면 스위칭이 사실상 불가능해진다.** 이 프로젝트는 이미 그 값을 치렀다 —
`id_registry.json` `_note_ability_id_policy`:

> **번호 재사용 금지.** … 재사용하면 DRIFT 로그·git 커밋 메시지·스펙 상호참조가 다른 것을 가리키게 된다.
> **재번호는 참조 5,194건 + 스펙 파일명 97개가 걸려 하지 않는다.**

`RM-BARRACKS-01`을 임시로 발급했다가 병영이 다른 곳으로 가면, 그때 걸리는 것은 스펙 파일·`LevelDesignMap` 행·
`rooms.json`·게임 `id_registry`·DRIFT 로그·커밋 메시지 전부다. **「임시」 표기는 그 비용을 줄여 주지 않는다.**

### 해법 — 축을 둘로 나눈다 (이 맵이 이미 하고 있는 방식)

`map_demo_layout`을 보면 방은 **이미** ID와 이름이 분리돼 있다:

| ID (불변) | label (자유) |
|---|---|
| `RM-ENTRY-01` | "Ward Threshold" |
| `RM-ADV-01` | "Open Combat Court" |
| `RM-OBJ-01` | "Dim Reliquary" |

→ **ID는 안정 축, 지역 정체성은 표시명·테마 축.** 그러면 *지역 컨셉이 바뀔 때 비용이 0*이 된다.
「실제 지역명 선반영」이라는 판정은 **정체성 축에서** 지켜지고, ID는 안 흔들린다.

> **주의 — 이건 앞서 고른 두 안(`PROTO` vs 실제 지역명) 중 어느 쪽도 아닌 세 번째 형태다.**
> 두 판정(*실제 지역명 선반영* + *컨셉 미확정, 나중에 스위칭*)이 **동시에 성립하려면** 이 형태여야 한다 —
> 아직 없는 이름을 ID에 선반영할 수는 없다. **초안 판단이며 확인이 필요하다.**

### 제안 명명 체계 (기존 패턴 준수)

| 종류 | 제안 | 근거 |
|---|---|---|
| 맵 | `MAP-UPPER-001` | 층 = 안정 축 |
| 청사진 | `DBP-UPPER-001` (`basedOn: DBP-DEFAULT-001`) | |
| 계약 | `CONTRACT-UPPER-001` | |
| 방 | **`RM-UPPER-01` … `RM-UPPER-09`** | **기존 패턴과 동일** — 데모가 이미 `RM-MID-01`·`RM-DEEP-01`로 **층 기반 방 ID**를 쓴다 |
| 풀 | `P-UPPER-01 …` | |
| 추출점 | `POINT-UPPER-01` / `-02` | 탈출 2점 |
| 컨셉존 | `ZONE-UPPER-001` **하나로 시작** | 지역 세분화는 컨셉 확정 후 — **`ZONE-` vs `CZ-` 접두사 판정도 같이 이연**(§4 이월) |

**번호는 전역에서 이어 받는다** — `RM-DEEP-01`이 데모 소유이므로 신맵의 심부 방은 `RM-UPPER-07` 등이 된다.
나중에 Mid/Deep 층이 생기면 `RM-MID-02`·`RM-DEEP-02`로 이어진다(재사용 없음).

### 정체성 축 — 여기에 **임시** 표기를 단다

```yaml
# rooms.json (게임) / RM-### (스펙) — ID와 별개 레이어
displayName: "병영 연병장"        # 자유롭게 교체
themeRef: THEME-BARRACKS          # status: Draft (임시) — 컨셉 확정 시 교체
```

| 방 | 초안 테마(**임시**) | 공간 문법 |
|---|---|---|
| `RM-UPPER-01` | 성문 어귀 | `safe` |
| `RM-UPPER-02` | 병영 | `choke` + 증원 |
| `RM-UPPER-03` | 기록원 | `los_broken` |
| `RM-UPPER-04` | 수문(목표 관통방) | `split` + 우회 |
| `RM-UPPER-05` | 제련소(보상 루트) | `open` + hazard |
| `RM-UPPER-06` | **(미명명)** 위험 관문 | `choke` + `entryRequirement` |
| `RM-UPPER-07` | **(미명명)** 심부 | `split` |
| `RM-UPPER-08/09` | **(미명명)** 탈출 ×2 | `safe` |

**테마 문서는 지금 만들지 않는다.** 지역 컨셉이 확정될 때 `LAY-UPPER` §7 또는 신규 Zone 문서에 등록하고,
그때 `themeRef`만 갈아 끼운다. **ID·경로·문법은 그대로 남는다.**
